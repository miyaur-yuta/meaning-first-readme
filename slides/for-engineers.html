Claude Code Harness × Spec Kit

意味ブロックを正本として、ハーネス設定と SDD ライフサイクルを一貫生成する設計

前提知識: Claude Code / Git / TOML / Markdown / Python

対象: Claude Code を業務利用するエンジニア・ハーネス保守者

所要: 約15分

Claude Code の7プリミティブ

README は CLAUDE.md の一部にすぎない

プリミティブ役割読込タイミング配置
CLAUDE.md常時効く文脈・指示セッション毎repo root / ~/.claude/
Skillsオンデマンド知識/ or 自動.claude/skills/<name>/SKILL.md
Hooks必ず発火する強制ルールライフサイクル毎.claude/settings.json
Subagents独立 ctx で専門作業委譲時.claude/agents/<name>.md
MCP外部システム接続ツール呼出時.claude/mcp.json
Plugins上記を束ねて配布install 時marketplace / path
Permissions許可スコープ/モード常時settings 群

権限モデル（スコープ × モード）

4スコープ（誰の設定か）

  • ~/.claude/settings.json — user
  • .claude/settings.json — project shared
  • .claude/settings.local.json — project personal (gitignored)
  • managed — enterprise, OS path

allow/deny/ask はスコープ間で merge。deny は常に優先。

6モード（どの程度自動か）

default acceptEdits plan auto dontAsk bypassPermissions

bypassPermissions は隔離環境（container/VM）のみ。rm -rf / 等のサーキットブレーカを除き全スキップ。

v1 では settings.json 系の自動生成は行わない。スコープ/モードの解説のみ提供（次段階で生成へ）。

単一の真実の情報源（single source of truth）

content/blocks/

各ブロックは TOML frontmatter（型付き）+ Markdown 本文。検証・監査・差分が全て機械可処理。

意味ブロック ↔ Spec Kit 対応

Spec Kit 入力意味ブロック種別備考
constitution.mdprinciple / constraint / decision不変原則
spec.mdpurpose / scope / non_goal / definition機能要件
plan.mdarchitecture / procedure技術計画
tasks.mdprocedure（具体化）実行タスク
検査入力evidence / fact / riskanalyze/converge
意味ブロックは 正本、Spec Kit は 工程。競合しない。

ビルドパイプライン

[content/blocks/*.md] │ ├─→ mfr validate (kind/status/trust 整合性) ├─→ mfr audit (多次元監査) ├─→ mfr benchmark (N-gram 検索の再現率) ├─→ mfr build (→ README.md, manifest) ├─→ mfr context (task 別に梱包) ├─→ mfr diff (スナップショット差分) └─→ mfr snapshot (完全性ハッシュ) ↓ 次段階 [constitution.md / spec.md / plan.md / tasks.md] ← Spec Kit [CLAUDE.md / Skills / Hooks / Subagents / mcp.json] ← Harness

v1 は上段のみ。下段（生成）は roadmap フェーズ2以降。

v1 の設計境界

✓ IN (v1)

  • 意味ブロック管理
  • README 生成・検証・監査・ベンチマーク
  • コンテキスト/差分/スナップショット

  • 説明資料（このスライド含む）

✗ OUT (次段階)

  • Spec Kit CLI ラッパ
  • 対話観察の自動化

「生成機能が範囲外」と「説明しない」は別物。概念・使い方・最小構成は v1 で提供。

リアルな対話品質（観察可能）

主観ではなく、ペルソナ別典型タスクでの観察基準

ペルソナ典型タスク成功基準
A: Claude Code 利用者「目的/次にやること/禁止事項」を聞くREADME の対象ブロックが最初の応答に反映
B: 保守者ブロック更新 → validate → audit根拠欠如を検証で弾ける
C: 初見読者README を開く → 全体把握AI 文脈との違いが分かる

観察結果は evidence ブロックとして蓄積。trust=observed 必須。サンプル1で判定しない。

ロードマップ

Phase 1 (v1, this PR)

README ビュー。Spec Kit は概念説明のみ。

Phase 2 — SDD integration

意味ブロック → constitution.md / spec.md / plan.md / tasks.md。clarify/analyze の支援。

Phase 3 — Harness generation

意味ブロック → CLAUDE.md / Skills / Hooks / Subagents / 権限。

Phase 4 — Plugin distribution

ハーネス一式を Plugin として配布。

拡張順は機能数ではなく、観測された引き渡し摩擦を減らす順。

python -m meaning_first_readme doctor

# 3. README 生成（自己ホスト）
python -m meaning_first_readme build --output README.md

# 4. 監査とベンチマーク
python -m meaning_first_readme audit
python -m meaning_first_readme benchmark

# 5. タスク別コンテキスト
python -m meaning_first_readme context \
  --task '公開前に事実・根拠・秘密情報・リリース条件を確認する' \
  --tokens 6500 --audience ai
