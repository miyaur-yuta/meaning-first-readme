# 説明時スクリプト（台本）

Spec Kit × Claude Code ハーネスの説明会用台本。初学者向け・エンジニア向けの両対応。

---

## 準備

- `slides/for-beginners.html` と `slides/for-engineers.html` を開いておく
- プロジェクタまたは画面共有で表示
- 听衆の構成に応じてどちらを使うか決める

## 初学者向け（for-beginners.html）

### Slide 1: タイトル (1分)

> 「今日は、Claude Code と Spec Kit という、AI と仕事するための仕組みについてお話しします。専門用語はなるべく使わず、比喩で説明します。」

### Slide 2: 「なんか違うものができた」 (2分)

> 「AI に『○○して』と頼んだら、違うものができた。こういう経験ありませんか？」

具体例を1つ出す:
- 「ファイルを整理して」と頼んだら、大事なファイルを消された等

> 「この『取り違え』を防ぐのが、今日の2つの仕組みです。」

### Slide 3: Claude Code とは (1分)

> 「Claude Code は、AI にいつでも見返せるルールブックを渡す仕組みです。」

比喩を使う:
- 新しいアルバイトさんに毎回ルールを説明するのは大変
- マニュアルを渡しておけば、AI がいつでも見返せる

### Slide 4: ルールブックの中身 (2分)

> 「ルールブックは1冊ではなく、目的別に7つに分かれています。」

主要な3つをピックアップ:
- CLAUDE.md = 基本ルール
- Skills = 必要な時だけ読むマニュアル
- Hooks = 絶対に守る禁止事項

> 「残りは専門的なので、詳しい人向けスライドで扱います。」

### Slide 5: 許可モード (1分)

> 「AI が勝手にファイルを消さないよう、何を自動でやっていいかを段階的に設定します。」

日常例:
- default = 毎回聞いてくる（初心者向け）
- acceptEdits = 編集は自動で（作業中）
- plan = 読むだけ（確認時）

> 「チームルールと個人ルールを分けられて、『ダメ』は常に優先されます。」

### Slide 6: Spec Kit とは (1分)

> 「Spec Kit は、GitHub 公式の作業手順テンプレです。」

発想の転換を強調:
- 従来: コードが王様
- Spec Kit: 指示書が王様、コードはそこから生まれる

### Slide 7: 9つの手順 (1分)

> 「Spec Kit は9つの手順を踏みます。全部覚えなくて大丈夫です。ポイントは『指示書を詰めてから、最後にコードを書く』という順番です。」

### Slide 8: 組み合わせ (1分)

> 「この2つを組み合わせると、人間は要点を伝えるだけで、AI がルールブックを作って、作業を続けてくれます。」

### Slide 9: 何が変わるか (1分)

> 「従来は README を人力で書いて、ルールを口伝えしていました。この仕組みだと、意味ブロックから自動で生成されて、AI が常に最新ルールを参照します。」

### Slide 10: まとめ (1分)

> 「Claude Code は AI にルールを読ませる仕組み。Spec Kit は指示書ファーストの手順。2つを組み合わせると、AI の取り違えを構造的に防げます。」

## エンジニア向け（for-engineers.html）

### Slide 1: タイトル (1分)

> 「Claude Code Harness と Spec Kit SDD を、意味ブロックという単一ソースから一貫生成する設計について話します。前提として Claude Code と Git と TOML を扱います。」

### Slide 2: 7プリミティブ (2分)

> 「Claude Code は README を含む包括的なハーネスです。7つのプリミティブがあって、README は CLAUDE.md の一部にすぎません。」

表を順に説明。強調ポイント:
- Hooks は `PreToolUse` 等のライフサイクルで必ず発火する
- Skills は `/` または自動判定で読まれる

### Slide 3: 権限モデル (3分)

> 「権限は スコープ × モード の2軸です。」

強調:
- `allow` / `deny` / `ask` はスコープ間で merge される
- `deny` は常に優先（user deny が project allow に勝つ）
- `bypassPermissions` は container / VM 専用

> 「本プロジェクトは v1 では権限設定の自動生成を行わず、解説のみを提供します。」

### Slide 4: SDD ライフサイクル (2分)

> 「Spec Kit は GitHub 公式の SDD フレームワークで、9フェーズからなります。」

ASCII 図を見せながら流れを説明:
- 上流: constitution → specify → clarify → plan → checklist
- 下流: tasks → analyze → implement → converge

> 「`/speckit.clarify` と `/speckit.analyze` が重要です。AI が能動的に質問し、整合性を検査します。」

### Slide 5: 意味ブロック (1分)

> 「本プロジェクトの正本は意味ブロックです。TOML frontmatter と Markdown 本文の組み合わせで、kind ごとに型が決まっています。」

### Slide 6: 対応表 (2分)

> 「意味ブロックと Spec Kit は競合しません。意味ブロックは正本、Spec Kit は工程です。」

表をなぞる:
- `principle` / `constraint` → `constitution.md`
- `purpose` / `scope` / `non_goal` / `definition` → `spec.md`

### Slide 7: パイプライン (2分)

> 「v1 のビルドパイプラインは上段のみ。下段（Spec Kit 生成・ハーネス生成）は次段階です。」

### Slide 8: 設計境界 (1分)

> 「v1 で作るもの、作らないものを明示しています。生成機能が範囲外でも、説明は提供します。この区別が重要です。」

### Slide 9: リアルな対話品質 (1分)

> 「主観ではなく、ペルソナ別典型タスクで観察します。観察結果は evidence ブロックに蓄積します。」

### Slide 10: ロードマップ (1分)

> 「Phase 1 が現 PR。Phase 2 で SDD 統合、Phase 3 でハーネス生成、Phase 4 で Plugin 配布。順序は機能数ではなく、観測された摩擦を減らす順です。」

### Slide 11: クイックスタート (1分)

> 「実際に動かすなら、この5コマンドです。Windows は `PYTHONPATH` の設定だけ注意。」

### Slide 12: リファレンス (1分)

> 「公式ドキュメントと本プロジェクトの主要ブロックへのリンクです。」

## 想定質問と回答

### Q1. ChatGPT や Copilot ではだめなの？

> A. 本プロジェクトは **Claude Code 限定** です（決定ブロック `decision.claude-code-only` 参照）。対象を絞ることで深度を上げています。他ツールへの拡張は明示的に範囲外です。

### Q2. Spec Kit を入れないと使えない？

> A. v1 は Spec Kit なしで動きます。Spec Kit は次段階（Phase 2）の統合対象で、現時点では概念説明のみです。

### Q3. README を手書きしてはいけない？

> A. `README.md` は生成物です。意味ブロック（`content/blocks/`）を編集して、`mfr build` で再生成してください。

### Q4. 認知負荷を下げる実践的な使い方は？

> A. `mfr context` を使って、タスクに必要なブロックだけを取り出せます。例えば「公開前確認」なら事実・根拠・秘密情報・リリース条件ブロックだけを 6500 トークンに収めて取り出せます。

### Q5. 権限設定を間違えたらどうなる？

> A. `deny` が優先されるので、user レベルで deny しておけば project レベルの allow には負けません。`bypassPermissions` だけは例外で、隔離環境以外では使わないでください。

### Q6. 観察結果をどう残す？

> A. `evidence` 種別ブロックとして、`decision.observation-format` のフォーマットに従って記録します。`trust=observed` を必ず付けてください。サンプル1で判定しないことが重要です。
