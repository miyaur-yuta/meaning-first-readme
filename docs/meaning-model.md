# Meaning Model

## 1. なぜ「意味」を実装対象にするのか

READMEは文章である一方、読者の判断を変えるインターフェースでもあります。文章が正しく見えても、目的、適用範囲、根拠、更新条件が欠ければ、別の読者は別の判断をします。本プロジェクトは「よい文章」を主観だけで評価せず、判断再現性へ分解します。

## 2. 運用定義

意味が達成された状態とは、読者またはAIが以下を再現できる状態です。

- 目的を識別する。
- 対象と対象外を区別する。
- 事実、前提、判断、推測を区別する。
- 根拠と依存関係を辿る。
- 妥当な次の行動を選ぶ。
- 不足、矛盾、期限切れで停止する。

この定義は哲学的な意味全般を説明するものではなく、文書システムを検証するための契約です。

## 3. 型

| kind | 要求される性質 |
|---|---|
| `purpose` | 最上位の達成条件 |
| `scope` | 適用対象 |
| `non_goal` | 拡大解釈の防止 |
| `definition` | 用語の運用定義 |
| `principle` | 複数判断へ適用する方針 |
| `assumption` | 未確定だが設計上採用する前提 |
| `fact` | 根拠または情報源が必須 |
| `constraint` | 違反してはならない境界 |
| `decision` | 選択理由が必須 |
| `architecture` | 構成要素と関係 |
| `procedure` | 受け入れ条件が必須 |
| `evidence` | 支持対象への逆参照 |
| `risk` | 失敗モードと対策 |

## 4. 関係

`depends_on`は成立または理解に必要なブロック、`evidence`は主張を支える根拠、`supports`は根拠側の逆参照です。文脈コンパイラは結論だけを切り出さず、依存閉包を一緒に選択します。

## 5. 合否

単一の意味スコアは作りません。構造、追跡可能性、行動可能性、鮮度、接続性、明瞭性を別々のゲートとして確認し、代表タスクに対する検索再現率を測ります。
